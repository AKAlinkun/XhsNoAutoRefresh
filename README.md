# XhsNoAutoRefresh

禁止**小红书 iOS 客户端**「一打开就自动刷新」，**完整保留**手动下拉刷新和上拉加载更多。

- 目标 App 包名：**`com.xingin.discover`**
  > ⚠️ **注意别搞混**：`com.xingin.xhs` 是**安卓**包名。iOS 是 `com.xingin.discover`（App 目录名也是 `discover.app`）。
  > 包名写错的话，插件装上会**一声不响什么也不做**。
- 适用环境：iOS 14 ~ 17.0 + TrollStore（巨魔）
- 注入方式：TrollFools 注入 dylib（无需越狱）
- **当前版本：v1.0.3 —— 早期安装版（本版只改「安装时机」，其余全是只读观测）**

---

## ★ v1.0.3：不是入口选错，是**时间**不对

v1.0.2 的真机弹窗把问题钉死了：

```
闸门安装于              启动后 4.2 秒      ← 这两行放在一起看
reloadData              13 次  首次 4.3s
endRefreshing            0 次
setState: 总写入         0 次
```

而用户看到的那次「打开就刷新」发生在**启动后 1~2 秒**。

**4.2 秒才挂上钩子，那一次刷新早就打完了 —— 我们完全没赶上。**

这也顺带解释了为什么所有刷新探针都是 `0`：不是入口不对，是**时间不对**。
（另外注意 `reloadData` 的首次时刻 4.3s ≈ 安装时刻 —— 说明在那 4.2 秒里 App 连布局活动都没有，
主线程被启动任务整段占住了。）

### 为什么原来会晚到 4.2 秒

v1.0.1 / v1.0.2 只把安装任务排到**主队列**上：

```c
dispatch_async(dispatch_get_main_queue(), ^{ XNRInstallWhenReady(0); });
```

而 App 启动时主线程被 dyld 加载几十个框架 + 自己的启动任务占满。
**排在主队列上的任务要等它整段跑完才轮到 —— 「排得早」并不等于「跑得早」。**
这是一个很容易踩的认知陷阱：我们以为 `dispatch_async` 到主队列就已经「尽早」了。

### 本版只改这一个机制：安装时机

| 改动 | 内容 | 为什么 |
|---|---|---|
| **① 后台早期安装** | 安装走 `dispatch_get_global_queue(PRIORITY_HIGH)`，首轮延迟 **40ms** 起步 | 后台队列**不等**主线程，能真正跑在刷新之前；40ms 是为了避开 dyld 加载镜像最密集的那一瞬间 |
| **② 持续重扫到 3 秒** | 每 80ms 再扫一轮，直到启动后 3 秒 | 晚加载的框架（`XYSpark` 自研 Swift 刷新头、React Native 控件）在头几百毫秒里**还不存在**，只扫一轮永远挂不上它们。（v1.0.2 里「第一轮成功就 `return`」也是同一个 bug 的另一种形态） |
| **③「已扫过的类」哈希集合** | 65536 槽静态表，见过就跳过 | 不这么做的话，每轮都要对**三万多类 × 4 个挂钩**沿继承链找方法，一轮就是几百毫秒 —— 持续重扫会把 App 启动拖垮。有了它，重扫的代价只剩「新出现的那些类」 |
| **④ `UIRefreshControl` 只读轮询** | 每 0.3 秒读一次 `scrollView.refreshControl.isRefreshing`，最多 21 秒 | 见下 |

### 为什么还要加「轮询外部刷新控件」

有个容易被忽略的事实：**`UIRefreshControl` 由 scrollView 内部驱动进入刷新态时，不经过 `-beginRefreshing`**
（那个方法是留给外部代码程序化调用的）。所以如果那个圈圈真是 `UIRefreshControl` 自己在转，
我们挂钩子永远挂不到 —— 只能从**结果侧**去观测 `isRefreshing`。

这一项是**纯只读**的：只读属性、只计数、不改任何东西。

### 每一处都做了什么安全保证

引入后台线程动 ObjC 运行时，是本版唯一的风险来源，所以逐条封住了：

- **铁律 2 没有被违反**：它禁止的是「**在 dyld 构造函数里立刻碰运行时**」。
  这里是构造函数**返回之后**、在另一个线程上执行，且首轮刻意延迟 40ms 避开镜像加载高峰。
- **整个过程只碰运行时，绝不碰 UIKit**：不读视图、不弹窗、不碰主线程状态。
- **自旋锁串行化**：确保「同一时刻只有一个安装者」，回到 v1.0.2 那种单线程写表的安全前提。
- **发布屏障**：写端「先写完 `gPatches[i]` 三字段 → `__sync_synchronize()` → 再让 `gPatchCount` 涨」；
  读端先同步再读 `count`。**顺序绝不能反** —— 反了的话主线程会读到「count 已涨、字段没写完」的垃圾条目 → 野 IMP → 崩。
- **加锁必配 `@finally`**：`return` / 异常都**不会**执行 `@try` 之后的普通语句，
  写成 `@try{} @catch{} [lk unlock];` 一旦提前 `return` 就永远不解锁 → 当场死锁。
- **容器读写配对加锁**：`gHookedNames`、`gTimeline` 由后台线程追加、主线程快照，
  原来（v1.0.2 全在主队列）不需要，现在**必须** —— 一边追加一边遍历 `NSMutableArray` 是会崩的。
- **不用 `usleep` 阻塞**：GCD 全局队列的工作线程数有限，`usleep` 按住线程 3 秒等于从线程池里借走不还；
  改成 `dispatch_after` 串联，**排完立刻归还线程**。
- **一键回退**：`kEarlyInstall = NO` 改一行就回到 v1.0.2 的主队列路径，其它功能不受影响。

### v1.0.3 同时修掉的两个「只有真机上才看得见」的问题

这一轮看完真机弹窗，顺手修了两处**不影响拦截逻辑、但影响"我能不能读懂数据"**的显示问题。
它们俩都属于同一类：**本地和 CI 都发现不了，只有真机弹窗上才暴露。**

**① 中文花屏（真 bug）**

v1.0.2 弹窗里那一行小标题显示成了：

```
— ÂåöÈ•ÉàçÊÖÑ —        ← 本该是「列表重载」
```

根因是我自己的写法：

```c
static const char *names[] = { "刷新事件", "列表重载", ... };   // 文件作用域，不能写 @"..."
[NSString stringWithFormat:@"— %s —", names[k]];               // ← 这里
```

**`%s` 在 NSString 的格式化里【不是按 UTF-8 解释】，而是按「平台默认 C 字符串编码」**
（Apple 平台上是 MacRoman）。把一个 UTF-8 的中文串交给 `%s`，必然花屏。
（`%s` 输出 ASCII 一直没问题 —— 类名、SEL、版本号都是 ASCII，所以只有中文暴露了这个坑。）

同类的第二处随后也被抓出来了：挂钩跳过原因（"已挂过"/"继承来的(避碰父类)"…）也是中文 `const char *` + `%s`。

**修法**：面向用户的文案一律写 `@"..."`；确实需要 `const char *` 的地方（SEL、类名、`strcmp` 用的原因值）
一律保持 ASCII，显示时再翻译。

**并且把它做成了自动检查**（`check_tweak.py` 第 13 条：**C 字符串字面量里不许出现非 ASCII 字符**）。

> ★ 实现这条规则时踩了个坑，值得记：第一版一跑就报 **42 个假阳性**。
> 因为 ObjC 允许**相邻字面量自动拼接** —— 那个 37 行的弹窗模板里**只有第一行带 `@`**，
> 后面每一行都是裸 `"..."`，它们**仍然是合法的 ObjC 字面量**。
> 现在的做法是：按出现顺序扫所有字面量，看它前面是 `@`、还是「紧接上一个字面量」，
> 后者就继承上一个的"是不是 ObjC 字面量"属性。
> **反例告警：一个报错几十处的检查，多半是检查本身写错了，不是代码错了。**

**② 「挂钩类数」这个标签是错的（会误导排障）**

v1.0.2 弹窗里写的是：

```
各挂钩命中          beginRefreshing=7 endRefreshing=4 setState:=14 reloadData=11
挂钩类数: 36
```

`36` 是**四个挂钩的方法总数**（7+4+14+11），根本不是"类数" —— 而"类数"是排查时最容易
用来判断"到底挂上几个刷新控件"的那个数。**标签错一个字，结论就差一条街。**

现在改成两行分开：

```
挂钩落脚点         36 处（其中 beginRefreshing 覆盖 7 个类）
启动宽限           关（空列表放行 开）
```

### 「挂钩的类」里那两个键盘类是什么？

真机列表里出现了：

```
UIKeyboardCandidateViewStyle      ← 噪声
UIKeyboardCandidateViewState      ← 噪声
MJRefreshComponent                ← MJRefresh 基类（子类继承它，日志里会看到子类名）
MJRefreshAutoFooter               ← 上拉加载更多
XYSparkModule.XYSparkRefreshHeader ← ★ 小红书自研的 Swift 刷新头，最可能就是那个圈圈
UIRefreshControl                  ← 系统控件
RCTTurboListRefreshControl        ← React Native 列表的刷新控件
```

前两个是 UIKit 里**恰好也实现了一个叫 `-beginRefreshing` 的方法**的类，和刷新毫无关系。
它们**永远不会被触发**（就是两条死记录），本版**故意不动过滤规则** ——
「一次只动一个变量」，这一版要验证的是"安装时机"，不该同时改命中规则。

### ★ 下一步的岔路：如果早装了还是 0，就要怀疑 「Swift 直接派发」

`XYSparkModule.XYSparkRefreshHeader` 是一个**Swift 类**（模块名带点）。
这里有个绕不开的机制问题：

> **`method_setImplementation` 只能改「走 objc_msgSend 的调用」。**
> Swift 对 `@objc` 但**没有 `dynamic`** 的方法，在 Swift 内部调用时可能走 **vtable / 直接调用**，
> 根本不经过消息派发 —— 那我们的钩子就永远不会被调用，哪怕钩子挂得再早、挂得再准。

这正好能解释「挂钩成功但一次都不触发」。**如果 v1.0.3 早装到 0.05 秒仍是 0，这就是头号嫌疑。**

验证它的办法**不是**去猜，而是靠这一版已经加进去的**第 ② 路只读观测**：
不看任何挂钩，直接看**几何结果** ——「列表是不是被程序性地拉下去了」。

```
列表静止在顶部：contentOffset.y == -adjustedContentInset.top
下拉露出圈圈：  contentOffset.y 会更小（更负），即 (-y) - inset.top > 0
再加上「没人在拖 / 没在惯性滑动」→ 就是 App 自己把列表拉下去的
```

它给出的正是**我们最缺的那个数：那一下到底发生在启动后第几秒**，以及**在哪个页面**。
（★ 这仍然是**只读**：只读 `contentOffset` 和 `inset`。铁律 3 禁止的是**写**几何值，不禁止读。）

> ⚠️ 一个已知的观测窗口限制：轮询本身必须跑在主线程上，而如果 App 启动时主线程被占满，
> 轮询的第一次采样也要等到主线程空下来才开始。所以 `轮询 ②` 如果报"未发生"，
> **不能**直接断定"列表没被拉下去" —— 要结合 `首轮扫描于` 和 `reloadData 首次` 的时刻一起看。

## ★ v1.0.2：真机数据推翻了我们的假设

v1.0.1 交付后，真机弹窗给出了**决定性的一条数据**：

```
本进程包名  com.xingin.discover  ✓匹配
挂钩类数: 7
beginRefreshing  触发 0 / 放行 0 / 吃掉 0
```

**7 个类全部挂钩成功**（含 MJRefresh 家族、XYSpark 自研 Swift 刷新头、React Native 的 `RCTTurboListRefreshControl`），
**但 `-beginRefreshing` 一次都没被调用。**

而用户明确看得见「下拉的那个圈圈」—— 界面上确实有刷新动作。
**结论：小红书这次的自动刷新，根本不经过 `-beginRefreshing`。**

> 这是本工程最重要的一次认知更新：
> **「挂上了钩子」≠「钩子会被调用」。** 挂钩成功的类数是一个很容易让人误以为快成了的指标，
> 但它只说明「这个入口存在」，不说明「App 走的是这个入口」。

### 所以 v1.0.2 不改拦截逻辑，只加探针

这一版**一行拦截逻辑都没动**，只加了三个**只读探针**（只数数、可能记一条调用栈、一律原样转交原实现）：

| 探针 | 为什么选它 |
|---|---|
| `-setState:` | **头号嫌疑**。MJRefresh 的圈圈一定会通过它进入 `Refreshing(3)` 态。如果 `beginRefreshing` 没被调用、它却被写成了 3，那真凶就找到了（调用栈会指出是谁写的） |
| `-endRefreshing` | 只要**真的刷过**，它一定会被调用 → 用它可以判定「刷新到底发生了没有」 |
| `-reloadData` | 刷新必然伴随数据重载 → 用它可以定位「那一刻」以及调用来源 |

同时弹窗新增两行关键信息：

- **`闸门安装于`** —— 钩子是在启动后第几秒挂上的。如果它比首次刷新**晚**，那说明我们根本没赶上（需要把安装时机提前）
- **`各挂钩命中`** —— 每个探针各挂上了多少个类。如果某个探针是 `=0`，那它的数据无效，得换个判据

**请把新弹窗（启动 10 秒后自动弹）整张截图发我**，据此决定 v1.0.3 拦哪个入口。

> ✅ 已收到，结论见上面 v1.0.3 一节：**不是入口不对，是时间不对。**

### 附：v1.0.2 首轮 CI 的一次编译失败（值得记）

```
Tweak.x:572:82: error: incompatible pointer types initializing 'const char *'
                with an expression of type 'NSString *' [-Werror,-Wincompatible-pointer-types]
  572 |     { "beginRefreshing", (IMP)&XNRHookedBeginRefreshing, XNRSigVoidNoArg, NO, @"拦截+计数" },
      |                                                                              ^~~~~~~~~~~~
```

**根因**：改表驱动时，`XNRGateDef.label` 字段声明的是 `const char *`，初始化却写成了 ObjC 的 `@"..."`。

**通则是这样一条**：**静态存储期的初始化器里只允许 C 常量表达式**。`@"..."` 在静态初始化里
既不是编译期常量，类型也对不上 —— 所以由**文件作用域**的 `static` 数组来装字符串时，
只能用 `"..."`。

**已把它变成一条自动检查**（`check_tweak.py` 第 6 条）：既查「文件作用域静态初始化块里有没有 `@"`」，
也查「单行静态变量是不是被非对象类型拿去接 `@"..."`」。
并且做过**反向测试**（故意把 `@"` 塞回去，确认检查真的 exit 1 且报出行号）——
不然这一关就是摆设。

## ★ v1.0.1 修了什么（这个坑值得单独记下来）

**现象**：装上了、注入成功，但**什么都不弹、也什么都不拦**。

**根因是我自己写的两段代码耦合在一起**：

```c
// 安装入口
if (![bid hasPrefix:prefix]) return;   // 包名不匹配 → 直接返回
...
// 而弹窗的计时基准只在安装成功时才被赋值
XNRInstallGates();                     // ← 里面才执行 gStartTime = XNRNow()

// 弹窗入口
if (gStartTime <= 0) return;           // ← 于是永远在这里返回
```

结果：**只要包名对不上，弹窗就被自己掐死了。**
而"没弹窗"这一个现象同时对应三种完全不同的原因，无法区分：

1. Dylib 根本没被加载（注入没生效）
2. 包名不匹配（守卫提前 return）
3. 包名匹配了，但一个刷新控件都没扫到

**教训：给用户看的诊断输出，绝不能挂在「目标判定是否通过」下面。**
诊断通道必须是**无条件**的 —— 否则它会在你最需要它的时候，恰好因为同一起故障而闭嘴。

**v1.0.1 的三处修改**：

| 改动 | 说明 |
|---|---|
| 包名不再作为硬开关 | TrollFools 本身就是「按 App 注入 dylib」，dylib 根本不会加载到别的 App 里 → 这层代码守卫是多余的。现在包名只用于日志和弹窗展示 |
| 计时基准与安装解耦 | `gStartTime` 改为在构造函数里就赋值 → **只要 dylib 被加载，弹窗就一定弹** |
| 弹窗改为最多重试 5 次 | 原来只试一次，一旦那一刻正好在页面转场动画里就永远不弹了（这点随机性足以让人排查半天） |

另外**弹窗第一行现在直接显示「本进程真实包名」** —— 一眼核对，不用再猜。

## 零、出事了怎么救（先看这段）

装插件后小红书打不开 / 闪退 / 卡住时，**30 秒恢复**：

1. 打开 **TrollFools** → 点 **小红书**
2. 插件列表里找到 **XhsNoAutoRefresh** → **左滑** → **删除**
3. 彻底杀掉小红书后台（上滑卡片）→ 重新打开

> TrollFools 的删除是「原位还原」，把 App 二进制里被改的那几段恢复原样，不丢数据。
> 若删掉插件后仍闪退 —— 那是没还原干净，用巨魔**重装一遍小红书**即可（App 数据在沙盒里，不会丢）。

**如果你能改代码（v1.0.3 专属）**：本版唯一的新增风险来自「在后台线程动 ObjC 运行时」，
所以专门留了一个**一键回退开关**：

```c
static BOOL kEarlyInstall = YES;   // ← 改成 NO，重新编译注入
```

改成 `NO` 之后，安装回到 v1.0.2 那条主队列路径（慢 4 秒，但行为和上一版完全一致），
**其它功能（拦截、探针、轮询）一个都不受影响** —— 这样就能把「是不是早期安装引起的」一刀切开。

## 一、为什么不能照抄 B站 那版

上一个同类工程（[BiliNoAutoRefresh](https://github.com/AKAlinkun/BiliNoAutoRefresh)）已经验证过一套完整方案，
但**直接套过来会失败**，有两处必须改：

| 差异 | B站 那版 | 小红书这版为什么必须改 |
|---|---|---|
| **命中规则** | 靠类名猜：类名里带 `Refresh` / 继承自 `BFC`/`BPlus`/`MJRefresh` 基类 | ❌ 小红书不一定用 MJRefresh，类名也可能完全不含 `Refresh`。**改成靠方法定义判定**：谁自己实现了 `-beginRefreshing` 且签名是 `v@:`，谁就是刷新控件 —— **框架无关** |
| **启动宽限** | 20 秒内一律放行，保首屏 | ❌ **会正好放过你要拦的那一次**：你要拦的就是「一打开就刷新」，20 秒宽限把它包在里面了。**改成用「列表里有没有内容」判断** |

### ★ 本版的核心机制：用「列表有没有内容」替代时间宽限

```
列表还没内容 → 这次是在【加载首屏】→ 放行（保首屏一定要能出来）
列表已有内容 → 页面已经渲染好了却还要自动刷新 → 这就是【多余的那一次】→ 拦
```

这条规则同时解决了两个互相矛盾的需求，而且它是**只读判断**（读 `contentSize.height`），
不写任何几何值，因此不会踩到「跟 App 布局互相纠正 → 卡死」那个坑。

> ★ **启动宽限已默认关闭**（`kStartupGrace = NO`）。原因：实测这次刷新是「打开小红书**直接就刷**」，也就是发生在启动后 1~2 秒内 —— 1.5 秒的宽限正好可能把它放过。
> 首屏安全由上面那个「空列表放行」负责，所以关掉宽限**不会**带来白屏风险。

## 二、拦截逻辑做什么、不做什么

**拦截动作只有一件事：拦 `-beginRefreshing`**

1. 用户自己在下拉 → 放行；上拉加载（footer）→ 放行；列表还没内容 → 放行；其余 → 拦掉、不执行原方法
2. 拦完**什么都不做** —— 不写几何值、不代叫 App 的 API、不弹窗

**明确不做（全部是上一个工程用真机血换来的坑）：**

- ❌ **完全不写任何几何值**（`contentOffset` / `contentInset` / `frame`）—— v1.4.0 挂几何热路径钩子导致布局死循环、App 卡死
- ❌ 不挂 `UIScrollView` 的任何方法
- ❌ **不代调** App 的语义 API（`endRefreshing` / `setState:` —— 直接发消息调用它们才是「下拉即闪退」的成因）
  > ★ v1.0.2 起 `-setState:` / `-endRefreshing` / `-reloadData` 被挂上了，但**只作只读探针**：
  > 数一下次数、必要时记一条调用栈，然后**原样转交原实现**，一个字节的行为都不改。
  > CI 里有一条静态检查强制这件事：探针函数体内必须出现 `XNROrigFor`（转交原实现的证据），
  > 同时禁止出现 `] setState:` / `] endRefreshing` 这种**直接发消息调用**的写法。
- ❌ 不自动弹窗（自动弹窗落在页面转场动画里会导致「进视频闪退」）
- ❌ 不在启动阶段动 ObjC 运行时（构造函数里只排延后任务）

## 三、★ 为什么这一版"不带收尾"

上一个工程的教训：**拦掉刷新之后，被 App 提前拉进下拉区的列表没人负责收回 → 界面卡在半拉状态**（往上划一下才能恢复）。

**能自愈、不危险，所以我们不在 v1.0.0 里治它。** 原因：

> 收尾必须写几何值，而写几何值正是上一个工程把 App 搞卡死过的那条路。
> 正确顺序是：**先确认这一版「拦得住 + 不闪退」，再单独加收尾** —— 一次只动一个变量。

如果装上之后出现了「返回/打开时列表半拉着」，告诉我，下一版加收尾（那部分代码在 B站 工程里已经验证可用）。

## 四、安全阀（纯本地逻辑，不与 App 交互）

| 阀 | 规则 | 防的是什么 |
|---|---|---|
| ① 启动宽限 | **默认关闭**（`kStartupGrace = NO`） | 本来想防「列表还没来得及渲染」，但实测这次刷新就在启动后 1~2 秒内，开着反而会把目标放过 → 关掉 |
| ② **空列表放行** | 刷新控件的列表**还没有任何内容** → 放行 | ★ 这是首屏加载，拦住就是白屏 |
| ③ 重试熔断 | 3 秒内被拦超过 **6 次** → 静默 **30 秒**全部放行 | App 反复重试刷新时被我们反复吃掉 → 死循环 |
| ④ 拿不到判断依据 | 读不到刷新控件的 `scrollView`、或不在主线程 → 放行 | 判不动就别动 |

**共同原则：任何异常情况一律放行。宁可漏拦，绝不卡界面。**

### 怎么判断「成没成」（v1.0.2 版）

| 现象 | 结论 |
|---|---|
| **`吃掉` ≥ 1** | ✅ 目标达成。打开时不再自动刷新了 |
| **`beginRefreshing 触发` = 0，但 `setState:Refreshing` > 0** | ★ **找到真凶了** —— 刷新走的是 `-setState:` 而不是 `-beginRefreshing`。（v1.0.3 实测这两个都还是 0，说明问题在**时间**上而不在入口上） |
| **`beginRefreshing 触发` = 0，`endRefreshing` > 0** | 刷新确实发生了，且被 `endRefreshing` 抓到了 → 用它的调用栈定位驱动点 |
| **`beginRefreshing 触发` = 0，`reloadData` > 0，其它都 0** | 刷新可能是几何驱动（`UIRefreshControl` 那类由滚动视图直接触发的），需要另想办法 |
| **探针全是 0，且 `闸门安装于` > 首次刷新时刻** | ❌ **钩子挂晚了** —— 刷新发生在安装之前。下一版要把安装时机往前提 |
| **探针全是 0，`闸门安装于` 很小（< 0.5s）** | 刷新根本没发生在这段时间里 → 说明需要在别的时间点观察（例如从「搜索页返回首页」那一刻） |
| **某个探针 `各挂钩命中` = 0** | 该探针没挂上任何类 → 它的 0 是「无效数据」，不能据此下结论 |
| **`吃掉` = 0，`触发` > 0** | ❌ 全被放行了。看「放行原因明细」是哪一条在放行 |
| ↳ 「列表还没内容」很多 | 说明目标刷新发生在**列表还是空的**时候。这不是多余刷新，是首屏加载 —— **那就没法拦**（拦了就是白屏） |
| ↳ 「用户自己在拖」很多 | 大概率是你自己在测试下拉，属正常 |
| **`触发来源` 后台线程不为 0** | 正常。但**不要**据此推断钩子在后台线程执行（上个工程在这里翻过车：实测过钩子其实在主线程，调用栈里的线程池符号只是"谁发起的"） |

> ★★ **弹窗是「切前台那一刻」拍的照片，不是实时仪表盘。**
> 必须**复现前后各切一次前台**对比数字差，单看一张快照会误判。

### 怎么判断「成没成」（v1.0.3 版，先看最上面这四行）

```
首轮扫描于         启动后 0.05 秒     ← ① 早期安装生效了吗
扫描轮次 / 最后一轮  37 轮 / 最后一轮在启动后 2.98 秒   ← ② 重扫跑满了吗
闸门安装于         启动后 0.06 秒     ← ③ 是不是真赶在刷新前面
beginRefreshing  触发 3 / 放行 2 / 吃掉 1   ← ④ 拦到了吗
```

| 现象 | 结论 | 下一步 |
|---|---|---|
| `首轮扫描于` 仍是 **4 秒多** | ❌ 早期安装**没生效**（还是走了主队列兜底） | 检查 `kEarlyInstall` 是不是被改成了 `NO` |
| `首轮扫描于` ≈ **0.0x 秒**，`触发 > 0` | ✅ **成了** —— 早装之后终于赶上了那次刷新 | 把 `kShowAlert` 改 `NO` 出日常版 |
| `首轮扫描于` 很小，但 `触发` 仍是 **0** | 确认了：**真的不走 `beginRefreshing`** | 看下两行 |
| `轮询：发现正在刷新` **> 0 次** | 那个圈圈是 `UIRefreshControl` 在被 scrollView **内部驱动** | v1.0.4 从 scrollView 侧拦，不从 `beginRefreshing` |
| `探针: 其中 Refreshing` **> 0** | 真凶是 `-setState:` | v1.0.4 改拦「写进 `3`」这一下 |
| 上面两个都是 **0** | 刷新不发生在观测窗口（21 秒）内，或压根不是这两种控件 | 换触发路径重现一次再截 |
| `扫描轮次` 只有 `1` 轮 | 重扫没跑起来（异常？被杀？） | 看沙盒日志 `XNR_fix.log` 的安装时间线 |
| `最后一轮在启动后` 明显 < 3 秒 | 某个轮次抛异常中断了链 | 同上，日志里会有 `⚠️ 安装轮次抛异常` |

> ★ 本版新增的「安装时间线」就是为这一步准备的：`#1@0.05s→2处  #2@0.13s→5处 …`
> 一眼就能看出「有没有在扫 / 每轮扫出多少 / 哪一轮开始扫不出东西了」。

### ★ 最重要的两行（v1.0.3 起变成四行）

```
首轮扫描于         启动后 0.05 秒
闸门安装于         启动后 0.06 秒
首次触发          启动后 2.3 秒 → 已吃掉 ⛔️
```

`闸门安装于` 是 v1.0.2 新加的，专门用来判断「我们有没有赶上」：

- 安装时刻 **早于** 首次刷新 → 我们赶上了，数据可信
- 安装时刻 **晚于** 刷新时刻 → 那次刷新在我们装钩子之前就打完了，**必须把安装时机提前**

日志同时写在沙盒 `Documents/XNR_fix.log`（Filza 可看）。

## 六、顶部开关（`Tweak.x`）

| 变量 | 默认 | 作用 |
|---|---|---|
| `kBlockRefresh` | `YES` | 总闸。`NO` = 只观察不拦（排障用） |
| `kShowAlert` | **`YES`**（诊断版） | `NO` = 不弹窗。**确认可用后改成 `NO` 就是日常版** |
| `kProbeTrigger` | `YES` | 记录刷新来源（哪个页面 + 调用栈，最多留 4 条、每 1.5 秒最多 1 条） |
| `kStartupGrace` / `kStartupGraceSecs` | **`NO` / `0.0`** | 阀① 启动宽限，**默认关闭**（见「一」的说明）。想开就改 `YES` 并把秒数填上 |
| `kSkipWhenEmptyView` | `YES` | **阀② 空列表放行（本版核心机制）**。`NO` = 不看列表内容，一律拦 |
| `kBreakRetryLoop` / `kCooldownSecs` | `YES` / `30` | 阀③ 熔断 |
| `kEarlyInstall` | **`YES`** | **★ v1.0.3：后台早期安装**（本版唯一的机制改动）。**改成 `NO` 即一键回退**到 v1.0.2 的主队列安装路径，其它功能不受影响 |
| `kEarlyFirstDelayMs` | `40.0` | 首轮后台扫描前的等待(ms)：给 dyld 一点时间，避开镜像加载最密集的瞬间 |
| `kEarlyRescanSecs` | `3.0` | 持续重扫到启动后多少秒。**别改成 0** —— 晚加载的框架（XYSpark / RN 控件）只有等它出现才能挂上 |
| `kEarlyIntervalMs` | `80.0` | 重扫间隔(ms)。`3.0s / 80ms ≈ 37 轮` |
| `kPollRefreshCtrl` | **`YES`** | 低频轮询 `UIRefreshControl.isRefreshing`（**纯只读**，最多 21 秒自动停）。用来回答「那个圈圈到底是不是 `UIRefreshControl`」 |

> ★ **三个只读探针没有开关，永远开着。** 它们的行为就是「数一下 + 原样转交原实现」，
> 开销可以忽略，而且一旦关掉，下次出问题就没有数据可看了。

## 九、已知限制

- **本版不带收尾**：如果出现「界面上拉/下拉到半拉位置」，划一下就能恢复，不危险 —— 见「三」。
- **如果小红书的首屏加载本身就靠这次刷新**（空列表 → 调 `beginRefreshing` → 拉数据）→ 我们**拦不了**，
  拦了就是白屏。这种情况只能换个思路（例如拦后续的、而非首次的）。
- 只拦「刷新」，**不拦页面被销毁重建**。
- 插件对**所有**非用户触发的刷新都生效（不只首页）。如果发现别的页面该刷新却不刷了，告诉我，可按页面收窄。
- **v1.0.2 是探针版**：拦截逻辑一行没改，所以「还是会刷新」是**预期现象** —— 这一版的目的就是把真凶抓出来。
- **v1.0.3 是早期安装版**：只改了安装时机，拦截逻辑同样一行没改，所以**有可能还是会刷新**（预期内）——
  这一版要回答的是「早装上去之后到底赶没赶上」。真正的拦截点定在 v1.0.4。
- **v1.0.3 的主要风险**是「在后台线程动 ObjC 运行时」（本工程第一次这么做）。
  已经用自旋锁串行化 + 发布屏障 + 首轮延迟 40ms + 全程不碰 UIKit 封住，并留了 `kEarlyInstall = NO` 一键回退。
  如果装上后**一开就闪退**，先把它改回去 —— 这样能立刻把「是不是这一项引起的」切开。
- **轮询只跑 21 秒**：`kPollRefreshCtrl` 每 0.3 秒一次、最多 70 次就自动停，不做长期轮询（不长期打扰 App）。
- 本插件只改本机 App 的交互行为，不修改服务端逻辑，不影响账号。

## 十、工程实现要点（给以后排障）

- **零 Logos**、不依赖 CydiaSubstrate：`-Wl,-dead_strip_dylibs` + `control` 里不写 `Depends: mobilesubstrate`
- **纯 objc runtime**：`objc_copyClassList` 扫类表 → `XNRClassDefines` 判断「这个方法是不是你自己实现的」
  → `method_setImplementation` 换实现，原 IMP 存进 `(Class, SEL)` 双键表，按继承链回查
- **签名校验**：只接受完全匹配的 type encoding（`v@:` = 无参；`v@:q` / `v@:i` / `v@:l` = 一个整数参数），
  用 `method_getTypeEncoding` 解析，防参数错位崩溃
- **挂钩表改成表驱动**（`XNRGateDef gGateDefs[]`），加一个挂钩只改数组一行，不用再复制粘贴二十行
- **「刷新控件家族」判定（v1.0.2 定稿）**：
  ```
  类名含 "Refresh"   或   该类自己实现了 -beginRefreshing
  ```
  两条并集 —— 单靠类名会漏掉名字奇怪的实现，单靠 `beginRefreshing` 会漏掉不实现它的自研控件
- **只读探针的三条纪律**：只数数、必要时记一条调用栈、**一律原样转交原实现**；
  `reloadData` 只挂 `UICollectionView` / `UITableView` 及其子类（否则会挂到全 App）
- **构造函数只排延后任务**，安装失败会多轮重试（间隔固定 0.3 秒），最多 5 轮
- **方法实现挂在父类上、子类继承** → 只扫到父类、子类照样被拦（日志里会看到事件来自子类名，属正常）
- **日志**：`Documents/XNR_fix.log`，只在放行/拦截这些低频事件写，热路径零文件 I/O

### ★ v1.0.3 起额外要守的并发纪律（引入后台安装后才有）

| 纪律 | 一句话理由 |
|---|---|
| 安装用**自旋锁**串行化（`__sync_lock_test_and_set`） | 后台早期路径与主队列兜底路径会同时扫，两边一起改 `gPatches` / `gPatchCount` 必崩 |
| 写端**先写完数据、屏障、再发布 count**；读端**先屏障再读 count** | 反过来的话读端会拿到「count 已涨、字段没写完」的垃圾条目 → 野 IMP → 崩 |
| 所有加锁必须配 **`@finally`** | ObjC 的 `return` / 异常**不会**执行 `@try` 之后的普通语句；提前 return 就永远不解锁 |
| 跨线程共享的容器（`gHookedNames` / `gTimeline`）**读写都加 `@synchronized`** | 一边 `addObject`、一边 `componentsJoinedByString:` = 崩；v1.0.2 全在主队列所以不需要 |
| **不用 `usleep` 长时间占住 GCD 线程**，改用 `dispatch_after` 串联 | GCD 全局队列线程数有限，按住 3 秒等于从线程池借走不还 |
| 容器在**单线程的构造函数里**就建好 | 省掉「两边都判 nil、同时建表」这类竞态 |

### 交付前静态自检（`check_tweak.py`，本地与 CI 共用同一份）

在花 1 分钟装 Theos 之前先跑，把低级错误和危险代码挑出来（失败给出 `::error` 注解 + 行号，比 clang 的一大屏好读）：

| # | 检查 | 不查会怎样 |
|---|---|---|
| 1 | 每个用到的 `kXxx` / `gXxx` 常量都必须有定义 | 上个工程就是一行常量被误删导致 `use of undeclared identifier` |
| 2 | 不许出现 Logos `%hook` / substrate 头文件 / substrate API | 铁律 1 被违反 → 一开就闪退 |
| 3 | **零几何写入**：`setContentInset:` / `setContentOffset:` / `setFrame:` | 铁律 3 被违反 → 布局死循环、App 卡死 |
| 4 | 禁止**直接发消息调用** `endRefreshing` / `setState:` / `reloadData` | 挂成只读探针是允许的；直接调用才是卡死成因 |
| 5 | 每个只读探针的函数体内必须出现 `XNROrigFor` | 有人把探针写成"只计数不转交" → 偷偷改了行为 |
| 6 | **文件作用域静态初始化器里不许出现 `@"..."`** | `-Werror,-Wincompatible-pointer-types`（v1.0.2 首轮 CI 就栽在这） |
| 7 | 括号平衡 | 语法错 |
| 8 | 关键函数只能有**一处真定义** | 曾按 `"\n}\n"` 定位删重复函数，误匹配内层闭包把函数截断、反而制造出重复定义 |
| 9 | **函数先定义后调用** + **实参个数与形参一致** | 隐式声明 / 参数错位；本机无 clang，只能靠这条兜住 |
| 10 | LF 行尾、无 UTF-8 BOM | make 的 include 行带 `\r` 报错 |
| 11 | **格式化字符串占位符数 == 实参数** | 弹窗那个 37 个占位符的模板，`initWithFormat:arguments:` 数量不符会**当场抛异常**，弹窗正好在那一刻炸 |
| 12 | **加锁函数里 `[.. lock]` 之后有 `return` 就必须有 `@finally`** | 提前 `return` 漏解锁 → 当场死锁（这是加锁时最容易犯、也最难查的错） |
| 13 | **C 字符串字面量（`"..."`，不含 `@"`）里不许出现非 ASCII 字符** | 真机事故：弹窗标题显示成 `— ÂåöÈ•ÉàçÊÖÑ —`。根因是 `%s` 在 NSString 格式化里按**平台默认 C 编码（MacRoman）**解释，不是 UTF-8。**这个 bug 编得过、跑得通，只有真机弹窗上才看得见** —— 而弹窗就是唯一的诊断通道，所以必须静态拦掉。中文文案一律写 `@"..."` |

> ⚠️ 正则会有**误报**，两类要人工放行：`@protocol XNRXxx` 声明、`typedef enum { XNRXxx, ... }` 枚举成员 ——
> 它们不是「未定义」，是脚本没识别 `@protocol` / 枚举体。**判定前先看这两处。**
>
> ★★ **反向测试已经内置**：`python check_tweak.py --selftest`
> 它会往好代码里**注入 10 种已知错误**（静态初始化用 `@"`、实参个数不符、常量被删、几何写入、
> Logos 钩子、探针不转交原实现、格式化占位符不符、加锁漏 `@finally`、C 字符串里写中文、括号不平衡），
> 逐一确认检查器真的 exit 1，**并且校验变异体自身是合法的**（括号平衡）。
> **CI 里也是先跑反向测试、再跑正式检查。**
>
> ★ 还有一个反过来用的读法：**如果一条新规则一跑就报几十处，先怀疑规则写错了。**
> 第 13 条第一版就报 42 个假阳性 —— 因为 ObjC 允许**相邻字面量自动拼接**，
> 那个 37 行的弹窗模板只有第一行带 `@`，后面每行都是裸 `"..."`，但它们仍然是 ObjC 字面量。
>
> 这一条不是形式主义 —— 本轮开发中先后抓到 **三次检查自身出问题**：
> ① 静态初始化块的正则没锚定「顶格 static」，`.` 一路吞到后面的代码里 → **误报**；
> ② 函数定义正则匹配不了 `NSString *Foo(` 这种「星号紧贴函数名」的返回类型 →
>    函数根本没进表，「先定义后调用」「实参个数」两条规则**静默失效**；
> ③ 探针检查用 `.*?\n\}` 取函数体，代码里花括号多一个时它会一路吞进**下一个函数**，
>    从邻居身上读到 `XNROrigFor` → **假阴性**（现在改成真正做花括号配对，并由 `--selftest` 的
>    「变异体必须自洽」检查兜住）。
>
> 三次都会以「自检通过 ✓」的形式骗过我们，然后在 CI 上炸。**没做反向测试的检查器不值得信。**
>
> ★★ 再补一条同类的认知：**「自检通过 ✓」只证明「我检查的那些项没问题」，不证明「代码能编译」。**
> 本工程两次 CI 失败都是检查器管不到的地方 —— 静态初始化类型不匹配、函数名字符串写错。
